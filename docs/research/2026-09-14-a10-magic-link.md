## Summary

1. **Version fit: plausible, not proven.** Latest release is `0.75` (2026-07-20), compiled against Keycloak `26.6.3`. `quay.io/keycloak/keycloak:latest` is `26.7.3`. No release note, CI matrix or maintainer statement confirms 0.75 on 26.7.x; the maintainer's own comments conflict (§1). Tested in our compose before A10 was accepted (see the banner above).
2. **The link cannot point at the app's domain.** The extension always builds `https://<keycloak-host>/realms/<realm>/login-actions/action-token?key=…&client_id=…`. Only the *post-login* `redirect_uri` is ours. §7.5 step 1 is wrong as written (§2).
3. **A mail scanner GET burns a single-use token.** Keycloak processes the action token on `GET`; it only skips `HEAD`. Neither Keycloak nor the extension offers a confirm click or POST-only consumption. The single-use flag is also **off by default** in both the authenticator config and the REST API (§3).
4. **No per-email send limit exists anywhere in Keycloak or the extension.** Keycloak brute-force detection covers "password, OTP and recovery codes" only. The 5/email/hour limit has to live in the BFF (§4).
5. **Upstream Keycloak 26.7 ships no email magic link or email OTP.** The same extension ships an Email OTP authenticator (browser flow only) and, since 0.7x, a **Login Token + direct-grant** path that lets a native app redeem a UUID at the token endpoint with no browser. That path fits D32 better than the action-token link (§5, §Recommended change).

## 2. Can the link point at the app's domain? How does the app finish the OIDC flow?

**The link is always on Keycloak's host.** `MagicLink.actionTokenBuilder` (src/main/java/io/phasetwo/keycloak/magic/MagicLink.java, lines 290–297):

```java
return Urls.realmBase(baseUri)
    .path(RealmsResource.class, "getLoginActionsService")
    .path(LoginActionsService.class, "executeActionToken")
    .queryParam(Constants.KEY, tokenString)
    .queryParam(Constants.CLIENT_ID, clientId);
```

`baseUri` is `session.getContext().getUri().getBaseUri()` (line 257), the Keycloak server's own base URL. There is no config to change the host or path. The README's sample response confirms the shape: `"link": "https://keycloak.host/auth/realms/test/login-actions/action-token?key=eyJhbG...KWuDyE&client_id=account-console"` Source: https://github.com/p2-inc/keycloak-magic-link#resource

**What is ours is `redirect_uri`.** The REST endpoint `POST /realms/{realm}/magic-link` (requires `manage-users`; `MagicLinkResource.java` line 33) validates it with `RedirectUtils.verifyRedirectUri(session, redirectUri, client)` (`MagicLink.validateRedirectUri`, line 285), so it must be in the client's Valid Redirect URIs, and can be `https://app.example.com/…` (a universal link) or a custom scheme. Phase Two's native-app post says exactly this: "Simply change the redirect_uri to be a registered URI scheme for the application. Once a user clicks that link in the email, extract the code param of the url, and use that to then issue requests to the token endpoint." Source: https://phasetwo.io/blog/magic-links-native-applications/

**How the app finishes.** The action token carries `rdu`, `scope`, `state`, `nce`, `cc`, `ccm` (redirect_uri, scope, state, nonce, code_challenge, code_challenge_method): `MagicLinkActionToken.java` lines 11–17. The REST request accepts `code_challenge` / `code_challenge_method` / `state` / `nonce` (`MagicLinkRequest.java` lines 40–50). On tap, `MagicLinkActionTokenHandler.handleToken` writes those into the auth session (lines 66–88), calls `user.setEmailVerified(true)` (line 112), then `AuthenticationManager.redirectToRequiredActions` (line 122). Keycloak finishes the browser login and redirects to `redirect_uri?code=…&state=…`. The app then does a standard `grant_type=authorization_code` exchange with its `code_verifier`. So: **the app exchanges an authorization code, PKCE-bound to the challenge the BFF passed when it requested the link.** That means the device that asked for the link must be the device that redeems it (fine for PRD §6.3, which is same-phone), and the BFF must receive the app's `code_challenge` with the email.

Consequence for the "laptop opens the link" case (§7.5 flow, acceptance 2): a laptop opening a Keycloak-hosted link runs the handler and *completes the login on the laptop's browser*, redirecting it to `https://app.example.com/…?code=…`. The code is useless without the phone's `code_verifier`, but the single-use token is spent (§3). The static-page design only works if the emailed URL is *not* the Keycloak URL; see Recommended change.

## 3. What happens when a mail scanner GETs the link?

Keycloak 26.7.3, `services/src/main/java/org/keycloak/services/resources/LoginActionsService.java`:

- Line 545–553: `@Path("action-token") @GET public Response executeActionToken(...)` → `handleActionToken(...)`. **A GET runs the handler.**
- Lines 555–566: `@Path("action-token") @HEAD public Response executeActionTokenHead()` returns `Response.ok()`, with the Javadoc: "Skip processing HEAD requests for action tokens as they are usually used by mail servers to validate links." Source: https://github.com/keycloak/keycloak/blob/26.7.3/services/src/main/java/org/keycloak/services/resources/LoginActionsService.java. So Keycloak's only scanner defence is ignoring `HEAD`. Scanners that issue `GET` (most link-rewriting gateways) are not defended.
- Line 708–711: `if (!handler.canUseTokenRepeatedly(token, tokenContext)) { LoginActionsServiceChecks.checkTokenWasNotUsedYet(token, tokenContext); authSession.setAuthNote(AuthenticationManager.INVALIDATE_ACTION_TOKEN, token.serializeKey()); }`, and `checkTokenWasNotUsedYet` throws `Messages.EXPIRED_ACTION` if `session.revokedTokens().contains(token.serializeKey())` (`LoginActionsServiceChecks.java` lines 291–295).
- The key is actually revoked in `AuthenticationManager.finishedRequiredActions` (line 1082: `String actionTokenKeyToInvalidate = authSession.getAuthNote(INVALIDATE_ACTION_TOKEN)`), i.e. when the login completes, which for a magic-link user with no pending required actions is the same GET. **One scanner GET = token burned, and a code delivered to the scanner** (unusable thanks to PKCE, but the user's tap then shows Keycloak's "expired action" error page).

Extension side:

- `MagicLinkActionTokenHandler.canUseTokenRepeatedly` returns `token.getActionTokenPersistent()` (line 46–49). The default is **reusable**: `MagicLinkActionToken.actionTokenPersistent = true` (line 37), authenticator config `ext-magic-allow-token-reuse` default `true` labelled "Allow magic link to be reusable" (`MagicLinkConfig.java` lines 53–58), and REST `reusable` default `true` ("If the token can be reused multiple times during its validity", README table). **D32's "single use" requires `reusable:false` explicitly.**
- The extension offers no confirmation page, no POST-only redemption, no JS landing page. README "Implementation Notes" only says: "action token handler needs to invalidate the action token after single use".
- Lifetime: default `60 * 60 * 24` seconds (`MagicLink.java` line 219, `MagicLinkRequest.expirationSeconds = 60 * 60 * 24`, config help text "Defaults to 86400 s (1 day) if not set"). The extension sets the JWT `exp` itself from `expiration_seconds`; PRD's 900 s must be passed on every request. **UNVERIFIED** whether the realm "User-Initiated Action Lifespan" caps it (the realm setting is documented at https://www.keycloak.org/docs/latest/server_admin/ under "Tokens": "User-Initiated Action Lifespan: The maximum time before a user's action permission expires"; the extension code does not read it).

What does prevent burn: the *emailed* URL must not be the Keycloak URL. Options, in order of least code:

1. **Login Token + direct grant** (extension ≥ 0.7x, `feat: Login Token Direct Grant authenticator`, PR #200 merged 2026-06). `POST /realms/{realm}/login-token` stores a UUID in `SingleUseObjectProvider` and returns `lt:{uuid}` (`LoginTokenResource.java`, Javadoc: "does not authenticate the user directly and does not build an OIDC authorization URL"). The app redeems it with `POST /realms/{realm}/protocol/openid-connect/token`, `grant_type=password`, form field `login_token=lt:{uuid}`: "No username / password is required" (`LoginTokenDirectGrantAuthenticator.java` Javadoc). Single-use is enforced atomically (`LoginTokenHelper` line 457: "Atomically reserves a non-reusable token for single use by recording lt:used:{tokenId}"). Default `expiration_seconds = 300`, `reusable = true` (must set `false`), `set_email_verified` flag available (`LoginTokenRequest.java`). A UUID in a static page's query string is inert: nothing consumes it until the app POSTs it. **This is the only path where a GET can never burn the credential.**
2. **Action token, wrapped.** Call `/magic-link` with `send_email:false`, and have `notify` email `https://app.example.com/magic?k=<Keycloak URL or key>`. The app then opens the Keycloak `action-token` URL in `ASWebAuthenticationSession` and receives the `code` on the universal-link `redirect_uri`. Scanner-safe (static page), but two hops, a system browser sheet, and Keycloak-rendered error pages for expired/used links (PRD §6.3 wants `InlineError` in the app).

## 4. Is there a per-email send limit?

- Keycloak brute-force detection: "The protection is applied only to authentication mechanisms prone to the brute force attacks. Keycloak applies it only to password, OTP and recovery codes." Parameters are per-user login *failures* ("Max Login Failures … 30 failures", "Quick Login Check Milliseconds … 1000 milliseconds"). Nothing counts emails sent. Source: https://www.keycloak.org/docs/latest/server_admin/#brute-force-attacks
- Keycloak's own advice for volume attacks is external: "Consider using intrusion prevention software (IPS)." (same section, "Downside of Keycloak brute force detection").
- Extension: `grep -ri "rate\|limit\|throttle" src/main/java` finds nothing for magic links. The only related feature is the Cloudflare Turnstile authenticator ("can be placed before any step in a login flow that needs bot protection (e.g., before Magic Link or Email OTP)"): bot gating, not a per-email quota. The Email OTP authenticator does hook brute-force on wrong codes (`AuthenticatorUtils.getDisabledByBruteForceEventError`, `EmailOtpAuthenticator.java` line 103), which is the OTP-guess side, not the send side.
- Keycloak 26.x release notes contain no email rate limiting (searched "rate limit" in https://www.keycloak.org/docs/latest/release_notes/).

Standard way for us: the BFF is the only caller of `/magic-link` or `/login-token` (it holds the `manage-users` service-account token), so the counter belongs there: a Redis `INCR` + `EXPIRE 3600` on `magic:<email>` (ARCHITECTURE §4.4 already has Redis). Nginx `limit_req` can add an IP-based layer but cannot key on email inside a JSON body. PRD §11 "rate limiting on the magic-link endpoint (5 per email per hour)" is therefore a BFF requirement, not a Keycloak setting.

## 5. Alternatives

**Upstream Keycloak.** Release notes for 26.0–26.7 (https://www.keycloak.org/docs/latest/release_notes/) mention passwordless only as WebAuthn/Passkeys ("Passkeys for seamless, passwordless authentication of users", 26.4.0). The features list (https://www.keycloak.org/server/features) has no `email-otp`/`magic-link` feature. Searches of the admin guide for "magic link", "email OTP", "email code" return nothing. **Keycloak 26.7 ships no native email magic link or email OTP.**

**Same extension, Email OTP.** README: "There is a simple authenticator to email a 6-digit OTP to the users email address … recommended to use this in an Authentication flow following the Username form." Code: `SecretGenerator.getInstance().randomString(6, SecretGenerator.DIGITS)` stored as an auth-session note (`EmailOtpAuthenticator.java` line 69–98); no explicit code TTL beyond the auth session; wrong codes feed brute-force. It is a **browser-flow form** (`otp-form.ftl`), so the iOS app would drive it through `ASWebAuthenticationSession`, not a native field. No direct-grant OTP variant exists in the repo.

**Same extension, Login Token direct grant**: see §3 option 1. Native, no browser, no action-token GET, clean `401 invalid_grant` "Invalid or expired login token" for the app to map to PRD §6.3's `InlineError`. Trade-off: it requires enabling the Direct Grant flow for the iOS client with `direct-grant-login-token` as REQUIRED (Javadoc "Placement"), and the Keycloak-issued tokens come from the password grant path (no `code`/PKCE; the secret is the 300-s single-use UUID that only the phone that requested it will POST). Also new (June 2026): fewer users than the action-token path.

**Apple side (unchanged by the above).** AASA: "place it in your site's `.well-known` directory … `https://<fully qualified domain>/.well-known/apple-app-site-association` … You must host the file using `https` with a valid certificate and with no redirects." Apple's CDN fetches it, "Devices check for updates approximately once per week after app installation." Source: https://developer.apple.com/documentation/xcode/supporting-associated-domains. Universal links: "When users tap or click a universal link, the system redirects the link directly to your app without routing through the person's default web browser or your website … If the person hasn't installed your app, the system opens the URL in their default web browser." Source: https://developer.apple.com/documentation/xcode/allowing-apps-and-websites-to-link-to-your-content. Apple's current pages do not name Mail explicitly; the tap-from-Mail behaviour is the generic `open(_:options:)` path. Two caveats from TN3155 (https://developer.apple.com/documentation/technotes/tn3155-debugging-universal-links): "Entering the URL directly into the web browser's address bar will never open the app", and a long-press choice "will set the default behavior for your device when following universal links from this domain in the future", so the fallback page can appear on a phone that *has* the app; it should carry a manual open (custom scheme `mymoneyrecap://…`, since a same-domain tap in Safari "opens that link in Safari").

## Recommended change to A10 (applied 2026-09-16; `ARCHITECTURE.md` A10 is the current wording)

Replace A10 with:

> **A10. Email sign-in: Phase Two `keycloak-magic-link` Login Token, redeemed by the app via direct grant.** Keycloak pinned to the image version matching the extension's `keycloak.version` (today `0.75` ↔ `26.6.3`; never `latest`). The BFF (service account with `manage-users`) enforces 5 requests per email per hour in Redis, then calls `POST /realms/mmr/login-token` with `{email, client_id:"ios", expiration_seconds:900, reusable:false, force_create:true, set_email_verified:true}` and hands the `lt:{uuid}` to `notify`, which emails `https://app.example.com/magic?lt=…`. On iPhone the universal link opens the app, which POSTs `grant_type=password&login_token=…` to the token endpoint and stores the refresh token (D61). On any other device Nginx serves the static `/magic` page ("Open this link on your phone", plus a `mymoneyrecap://magic?lt=…` button); the page makes no request, so a scanner GET cannot consume the token, and the token is only consumed by the app's POST. Expired/used tokens surface as `401 invalid_grant` → PRD §6.3 `InlineError`.

If the team prefers to keep the authorization-code/PKCE shape, the minimum fix to the *current* A10 is: (a) `send_email:false` on `/magic-link`, our own email carrying the app-domain wrapper; (b) `reusable:false`, `expiration_seconds:900`, app-supplied `code_challenge` on every request; (c) the app opens the unwrapped Keycloak URL in `ASWebAuthenticationSession` and exchanges the `code`; (d) the Keycloak image pinned to 26.6.x until the extension states 26.7 support. Either way, the first task was a compose smoke test of `0.75` on the pinned image, the piece no source verified; it is `infra/compose/a10-smoke.sh`.
